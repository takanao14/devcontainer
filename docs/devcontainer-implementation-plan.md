# Devcontainer 実装計画

## 目的

macOS の IDE はホスト上のプロジェクトを開き、bind mount でコンテナと同じソースを共有する。
IDE からコンテナへの接続は任意であり、共通環境の成立条件には含めない。
Codex CLI、Claude Code、ビルド、
テストはコンテナ内で実行する。ホストのファイルシステムへのアクセスは、
明示的にマウントしたディレクトリに限定する。コンテナが主な分離境界であり、
マウント、実行権限、ネットワーク、デバイスへのアクセスがエージェントの操作範囲を決める。

プロジェクトごとのコンテナ内 CLI は、スマホから指示・承認・結果確認を行うリモート利用に
対応する。リモート用コンテナの稼働は、操作端末や IDE の接続状態から独立する。
Codex は標準の管理 daemon を使用し、ペアリングと環境の起動・停止は別操作とする。
tmux は前面実行する CLI を維持するための任意の手段とする。
独自の daemon 管理は通常利用の前提に含めない。
Codex の標準の管理 daemon の起動・停止は、リモート利用のライフサイクルに含める。
接続方式と検証状況は[リモート利用調査](remote-access.md)に記載する。

## 1. 共通イメージ

- ベース OS は Ubuntu 26.04、実行ユーザーは非 root の `developer`。
- イメージは Git、Make、GCC/G++ と共通の基本ツールを備える。
  検索・データ処理・シェル検証には rg、jq、Mike Farah yq v4、ShellCheck を備える。
- イメージは Codex CLI、Claude Code と必要なランタイムを備える。
  利用端末はネイティブアーキテクチャで必要なイメージをビルド・検証する。
  Forgejo CI は Docker を必要としない静的検証を担い、ビルド・公開は行わない。
- CLI は明示的な更新ビルド時点で公開後48時間以上経過した正式リリースを使用する。
  取得期限と実際のバージョンはイメージ内に記録する。
  通常ビルドはキャッシュを利用でき、更新ビルドはキャッシュを使用しない。
- 候補イメージは一意のローカル参照を持ち、検証失敗で利用中の参照を置き換えない。
  派生イメージは同じ更新単位で検証した共通イメージを使用する。
- CLI の更新単位はイメージ。実行中の自動更新は無効とし、更新通知とは別に扱う。
  Codex の管理 daemon はイメージ内の完全な CLI パッケージを使用し、
  `updater.autoUpdateEnabled` は false とする。状態ボリュームの過去のパッケージは
  起動時の選択対象に含めず、認証・ペアリング・履歴と他の設定は保持する。
- 旧イメージは少なくとも1世代保持する。更新前には停止した状態ボリュームを
  バックアップでき、復帰時には必要に応じて対応する状態を復元できる。
- CI の runner ラベルは `ubuntu-24.04`。起動条件は main の push、pull request、手動実行。
  通常運用にレジストリ、公開用 Secret、ARM64 runner を必要としない。
  移行の詳細と検証条件は[ローカルビルド計画](local-build-plan.md)に記載する。
- sudo の実行にはパスワード認証が必要。パスワードなしでの実行は許可しない。
- イメージに認証情報や個人設定を含まない。

## 2. プロジェクトの分離とマウント

- 原則としてコンテナごとに一つのプロジェクトを扱い、共通イメージを使用する。
- 主プロジェクトの絶対パスを `PROJECT` で受け取る。
- 主プロジェクトのマウント先と作業ディレクトリは `/workspace/<project-name>`。
  マウント方式は読み書き可能なバインドマウントとする。
- 他のプロジェクトを含む親ディレクトリは自動マウントの対象外とする。
- 他のリポジトリは、複数のプロジェクトを扱うために明示的に指定された場合だけマウントする。
- 既定のマウント対象にホストのホーム、SSH 秘密鍵、クラウド認証情報ファイル、Docker ソケットを含めない。

## 3. YAML による追加マウント

YAML 設定ファイルのパスを `MOUNTS` で受け取る。

```yaml
readOnly:
  - /path/to/app-a
  - /path/to/app-b

readWrite:
  - /path/to/app-c
```

- 両方のリストで複数のディレクトリと空白を含むパスに対応する。
- 追加ディレクトリのマウント先は、それぞれ `/workspace/<directory-name>` とする。
- 参照用リポジトリは読み取り専用とし、変更が必要な場合だけ読み書きを許可する。
- 設定例の配置先は `mounts.example.yaml`。`mounts.local.yaml` は Git の管理対象外とする。
- ホスト側のランチャーは Bash を使用し、YAML の JSON 変換は Mike Farah yq v4、
  構造・値の検証は jq の責務とする。Python への依存は含まない。
- コンテナ起動前に、不正な YAML 構造、未知のキー、相対パス、存在しないディレクトリ、
  パスの重複、アクセスモードの競合、主プロジェクトとの重複、マウント先名の衝突、
  アクセス権限が競合する親子ディレクトリの重複マウントを拒否する。

## 4. Makefile とランチャー

操作の入口は Make。検証とコンテナコマンドの組み立ては共通ランチャーの責務とする。

| ターゲット | 用途 |
| --- | --- |
| `build` | 通常利用または開発用のローカルイメージをビルドする |
| `rebuild` | 明示的にベースイメージを更新し、キャッシュなしで再ビルドする |
| `pull` | 任意の配布イメージを取得する |
| `shell` | 選択したプロジェクトのシェルを起動する |
| `codex` | Codex CLI を起動する |
| `claude` | Claude Code を起動する |
| `codex-remote-start` | 端末から独立した Codex リモート環境を起動する |
| `codex-remote-stop` | Codex とコンテナを停止し、状態を保持する |
| `codex-remote-pair` | 稼働中の環境に対するペアリングコードを発行する |
| `codex-remote-shell` | 稼働中のリモート環境のシェルに接続する |
| `codex-remote-status` | リモート環境の状態を確認する |
| `help` | 利用できる操作を表示する |

`run` は `shell` の別名とする。起動対象は利用側が指定した検証済みローカルイメージであり、
取得と起動はローカルビルドから独立した操作とする。
`codex-remote` は `codex-remote-start` の別名とする。

```sh
make codex PROJECT=/path/to/homelab NETWORK=bridge
make claude PROJECT=/path/to/app-a NETWORK=bridge
make codex PROJECT=/path/to/homelab MOUNTS=mounts.local.yaml NETWORK=bridge
```

### リモート利用のライフサイクル

- リモート用プロセスは選択したプロジェクトのコンテナ内で動作し、通常の CLI と
  同じマウント、認証状態、承認設定を使用する。
- 操作端末の終了・切り離しでは、リモート用コンテナと Codex の接続は継続する。
- ペアリングコードの発行は明示的な操作とし、通常の起動では発行しない。
  同じ Codex 状態ボリュームによる再作成後も、保存済みのスマホの接続登録を再利用する。
- 環境の停止操作は `codex remote-control stop` による管理 daemon の停止と、
  コンテナの停止を含む。シェル接続の終了は環境の停止とは独立する。
- 環境の明示的な終了と処理可能な終了シグナルでは、CLI の停止処理が
  コンテナ終了に先行する。停止に失敗した場合は利用者に通知し、待機時間には上限を設ける。
- コンテナの強制終了や Docker の停止では、コンテナ内の全プロセスが終了する。
  この経路では CLI の正常な停止や実行中の作業の完了を保証しない。
- コンテナ再作成後は明示的な起動操作を必要とし、保存済みの認証・接続登録・履歴と
  実行中の接続・作業を区別する。独自のホスト daemon や自動再起動は使用しない。

## 5. 認証・設定・履歴

- 永続化には、主プロジェクトごと、CLI ごとに独立した名前付きボリュームを使用する。
- プロジェクト識別子は絶対パスに基づく安定した値とし、同名ディレクトリのプロジェクト間でも衝突しない設計とする。
- Codex の設定、認証情報、履歴は専用ボリュームに永続化する。
- Claude の状態は専用ボリュームに永続化し、`CLAUDE_CONFIG_DIR` はその保存先に設定する。
  別途保存されるアカウント・設定ファイルも永続化の対象とする。
- 初回のサインイン場所はコンテナ内とする。ホストのエージェント設定全体や認証情報はコピーの対象外とする。
- 認証情報・設定・履歴はコンテナ再作成後も保持される。
- 複数プロジェクトを扱うセッションでは、主プロジェクトの設定と履歴を使用する。

## 6. 権限と分離境界

- CLI 内部のサンドボックスは任意の追加制限であり、共通環境の成立条件には含めない。
- 両 CLI の承認チェックは既定で有効。承認は操作前の確認、コンテナは
  アクセス可能な資源の制限を担い、それぞれ独立した設定とする。
- CLI 内部のサンドボックス用の依存関係と設定は追加プロファイルに属する。
  内部サンドボックスを使わない場合も、承認チェックを一括で回避する設定は使用しない。
- 非 root 実行、必要最小限のケーパビリティ、ホスト資源の限定的なマウントを基本とする。
  privileged モード、ホストの PID・ネットワーク名前空間、デバイスの公開は既定で使用しない。
- 追加の権限やデバイスへのアクセスは、明示的に選択するプロファイルに限定する。
- sudo のパスワード認証を、ファイアウォールなどの分離制御を保護する唯一の手段としない。
  エージェントの実行環境から分離制御を変更できないことを要件とする。
- 書き込み可能なバインドマウントでは、エージェントがホストのソースファイルを変更・削除できる。
  変更の確認・復旧手段は Git とバックアップとする。

## 7. ネットワーク制御

- 通信不要の実行の既定値は `NETWORK=none`。認証・推論・リモート接続などの
  オンライン利用では `NETWORK=bridge` を明示する。
- bridge はインターネットと到達可能な内部サービスへの通信を許可する。
  ホストファイルのマウント制限は通信先の制限を兼ねない。
- 許可リストは追加の制限を必要とする用途向けの任意のプロファイルとし、
  共通環境や派生イメージ開発の成立条件には含めない。
- 制限付きプロファイルでは、初期化権限とエージェントの実行権限を分離し、
  エージェントによる制御の変更や迂回を許可しない。DNS 更新への追従、
  リバインディングへの対処、OrbStack 上の動作を要件とする。

## 8. プロジェクト別イメージ

用途別イメージは共通のエージェント環境をベースとする。
各派生イメージの前提は、共通環境が検証済みであること。

| イメージの用途 | 追加ツール |
| --- | --- |
| Go/API | Go、Buf |
| Rust/LED | Rust、Cargo、rustfmt、Clippy、protoc、pkg-config、ALSA 開発用ヘッダー、Python、Ansible |
| DNS | dnscontrol、SOPS、age、direnv |
| インフラ | Terraform、Terragrunt、Packer、QEMU ツール、Ansible コレクション、kubectl、Helm、Helmfile、helm-diff、k0sctl、Cilium CLI、yq、ShellCheck、rclone、OpenBao CLI |

[プロジェクト別ツール一覧](project-tools.md)と homelab に取り込まれた mise 設定を
バージョンの参照元にする。Go と dnscontrol はプロジェクト間でバージョンが異なるため、
共通バージョンの採用には互換性の検証を必要とする。
各イメージは一覧で確認されたインタープリターとツールの依存関係も備える。

### OS パッケージ以外の管理（採用案）

- 配布バイナリーの管理は、固定した mise と用途別の設定・ロックファイルを使用する。
  OS のライブラリと開発用ヘッダーは引き続き APT の管理対象とする。
  Codex・Claude の取得はローカルイメージ更新方針に従う。
- dotfiles の共通ツール宣言は、参照コミットと取り込み元を記録した必要項目のみの
  スナップショットとする。個人設定・SSH 設定・chezmoi のホスト構築処理は含めない。
  ビルドの入力はこのリポジトリに保存し、ホストの dotfiles や upstream の main に依存しない。
- プロジェクト固有のバージョンと追加ツールは、このリポジトリの用途別設定で管理する。
  dnscontrol 5.3.0、Go 1.27.1、Buf 1.73.0 などの既存要件は、方式の変更だけでは更新しない。
- 新しいアプリケーションのバージョン選択は公開後48時間を待つ。
  mise の動的な選択と Python 依存の新規解決は `minimum_release_age = "2d"`、
  npm の CLI・依存取得はビルド時点の48時間前を `--before` の期限とする。
  固定値と既存ロックの再利用には追加の待機時間を設けず、固定値の変更時に公開日を確認する。
  Renovate の更新候補も2日以上経過したものを対象とし、公開日時が不明な候補は採用しない。
  この方針の対象はアプリケーションの選択であり、APT の配布・セキュリティ更新には適用しない。
- mise のバージョンと配布チェックサム、用途別ロックの Linux x64 / ARM64 の
  配布 URL・チェックサムは記録済みの入力とする。ビルド時の導入は `--locked` とし、
  対応バックエンドの必要なロック情報が欠ける場合は失敗する。ロック生成は更新工程に属する。
- 導入先は root 所有のイメージ領域。通常実行の PATH は導入済みバイナリーへの固定参照を
  使用し、作業ディレクトリの mise 設定・シムによる暗黙の変更は含めない。
  ユーザーによる明示的な別ツール導入は、イメージの更新・検証とは別の操作として扱う。
- Python アプリケーションのロックは、固定した uv が解決した依存グラフと
  配布物のハッシュを含む。mise.lock とネイティブの pyproject.toml・uv.lock は
  一体のビルド入力であり、導入時に再解決しない。Python 自体は APT の管理対象とする。
- Rust のバージョン・プロファイル・コンポーネントは mise の宣言・ロックの対象とする。
  配布物の取得・検証は rustup の責務であり、mise.lock の URL 固定と同等には扱わない。
  rustup 自体は固定した配布物を公開チェックサムで検証する。
- 更新は参照元の取り込みまたは用途別宣言の変更、ロック生成、レビュー、CI 検証を経た
  ローカルでのビルド・検証・切り替えとする。用途別ロックの生成・再生成の差分検査は
  利用端末、宣言と保存済みロックの整合性検査は Forgejo CI の責務とする。

ロックの保証範囲はバックエンドと mise のバージョンに依存する。
最新ドキュメントの機能を固定した mise に適用できることは、個別の検証を必要とする。
[公式のロック仕様](https://mise.jdx.dev/dev-tools/mise-lock.html)

## 9. 検証

- リモート用ランチャーの起動、操作端末の終了後の継続、CLI の明示的な停止、
  通常終了・終了シグナルでの停止順序と停止失敗時の扱いを確認する。
- コンテナ終了後にリモート操作できないことと、再作成後の明示的な起動・再接続を確認する。
- Ubuntu 26.04 上でビルドが成功し、両 CLI が `developer` として起動することを確認する。
- サインインと、認証情報・設定・履歴の永続化を確認する。
- ソースの変更がホストの IDE に反映されることを確認する。
- 他のプロジェクトや未マウントのホストパスへ、既定ではアクセスできないことを確認する。
- 読み取り専用マウントで書き込みが拒否されることを確認する。
- 複数マウント、空白を含むパス、不正な設定、重複、親子マウント、マウント先の衝突をテストする。
- Docker ソケットが利用できないことを確認する。
- bridge で認証・推論・リモート接続が動作し、none で外部通信できないことを確認する。
- 制限付きプロファイルを採用する場合は、許可・拒否された通信先への接続、DNS 更新への
  追従、リバインディングへの対処を OrbStack 上で検証する。
- 非 root 実行、ケーパビリティ、名前空間、デバイスへのアクセス制限と承認の動作を検証する。
- CLI 内部のサンドボックスに依存せず、コンテナのマウント・権限制御が機能することを確認する。
  追加プロファイルでネットワーク制限や内部サンドボックスを使う場合は、その制御も検証する。
- ローカルの更新ビルドで CLI の取得処理が実行され、記録したバージョンと実行するバージョンが一致することを確認する。
  更新後も起動・認証・承認・永続化が機能し、実行中に CLI が自動更新されないことを確認する。
- 候補イメージの起動・ツール・ユーザー権限を検証し、失敗した候補を利用しないことを確認する。
- 指定したローカル参照での起動、旧イメージへの復帰、必要に応じた状態ボリュームの復元を確認する。
- 派生イメージ内で代表的なプロジェクトのビルドとテストを行う。
  検証だけのためにインフラをデプロイしたり、ハードウェアへアクセスしたりしない。

## 10. 文書

README の記載対象は、CI・ホスト・コンテナの役割、ローカルイメージのビルド・選択・起動、
ローカル検証、単一・複数プロジェクトの例、
YAML 設定、初回サインイン、CLI の更新・バージョン確認・旧イメージへの復帰、
永続化ボリュームのバックアップ・復元、認証情報の削除、ネットワーク選択、
ソースの復旧方法とする。ランチャーのホスト側依存関係も記載対象に含める。
コンテナによる資源の制限・CLI の承認・任意の内部サンドボックスの
役割を説明する。分離上の制約として、マウントしたソースやコンテナ内の認証情報には
対応する権限を持つプロセスからアクセスできることを明記する。

## 実装順序

アプリケーション管理方式の検証は次の順序とする。

1. 固定した mise と用途別設定・ロックの配置、および取り込み元の記録方法を用意する。
2. DNS イメージの4ツールを同じバージョンのまま mise 管理へ移し、バージョン一致・
   オフライン検査・暗号化のテストと、ロック不足・不正チェックサムの拒否を確認する。
3. Linux x64 / ARM64 のロック生成・差分検査を利用端末で行い、静的な整合性検査を CI に組み込む。
4. 共通ツールと Go/API に展開する。Rust のコンポーネント指定と Python の推移的依存の
   ロック再現・破損拒否を確認し、Rust/LED に適用する。インフラ用イメージは別途実装する。

共通・派生イメージは利用端末のネイティブアーキテクチャでビルド・検証する。
