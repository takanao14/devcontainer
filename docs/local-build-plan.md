# 利用端末でのビルドへの移行計画

## 目的と対象

利用端末が1〜2台の運用では、各端末が必要な共通・派生イメージをビルドする。
Forgejo CI の責務は、イメージを生成しない静的検証とする。
本書は実装前の計画であり、既存の CI ビルド・公開方針を置き換える設計を定める。
コンテナの分離、マウント、承認、認証状態、リモート接続の設計は既存計画に従う。

## 望ましい構成

| 項目 | 責務と制約 |
| --- | --- |
| Forgejo CI | ランチャーのモックテスト、シェル解析、宣言と保存済みロックの整合性検査 |
| 利用端末 | ネイティブアーキテクチャでのビルド、ツール・権限・マウント・永続化・リモート終了処理の検証 |
| ロック更新 | 利用端末の専用コンテナで生成し、宣言・チェックサム・関連する検証値と一緒にレビュー |
| Renovate | 公開後48時間を経過した更新候補の提案。自動マージは無効 |
| レジストリ | 通常利用の依存先に含めない。既存成果物の削除は移行とは別の管理操作 |

CI は Docker CLI・daemon・レジストリ認証を必要とせず、イメージのビルド、
コンテナの起動、ロックの再生成、レジストリへの公開を行わない。
他のリポジトリと共有する runner の Docker 設定やキャッシュ管理は本変更の対象外とする。

## バージョンと更新

- mise、用途別ツール、チェックサム、依存ロックはレビュー済みの入力を使用する。
  導入は既存の locked 方針に従い、通常ビルドでロックを更新しない。
- Codex・Claude は更新ビルド時点で公開後48時間以上経過した正式リリースを選択する。
  取得期限と実際のバージョンはイメージ内に記録する。
- 通常の `build` はキャッシュを利用する。明示的な `rebuild` はベースを取得し直し、
  キャッシュなしで CLI を含めて更新する。定期的な自動更新は通常運用の要件に含めない。
- 実行中のコンテナ内の CLI 自動更新は無効とし、更新単位はイメージとする。
- 同じコミットでも、動的に選択する CLI と APT の取得時点が異なれば成果物は異なり得る。
  端末間でバイナリーが完全に一致することは保証しない。

## ローカルイメージの選択と復帰

更新候補と現在利用中のイメージは別の参照を持ち、ビルド・検証の失敗では利用中の参照を
置き換えない。候補タグはコミット、アーキテクチャ、ビルド識別子を含み、再利用しない。
ビルド識別子は時刻だけに依存せず、同時実行でも衝突しない値とする。
記録対象はソースのコミットと未コミット変更の有無、イメージ ID、アーキテクチャ、
CLI・用途別ツールのバージョン、検証結果とする。

派生イメージは、同じ更新単位で検証した共通イメージをベースにする。
検証済みの共通イメージを暗黙に再ビルドすることはなく、必要な派生イメージだけを生成する。
利用者は `IMAGE_REF` で検証済みの参照を選択する。旧イメージは復帰用に少なくとも1世代保持する。
再ビルドだけでは稼働中コンテナを更新せず、選択した参照での再作成が更新の境界となる。

認証・ペアリング・履歴のボリュームはイメージから独立する。
状態形式の互換性を保証できないため、更新前には対象環境を停止して状態をバックアップし、
旧イメージへの復帰では必要に応じてそのバックアップを復元する。
イメージ・キャッシュの整理は明示的な利用者操作とし、通常のビルドや CI に全体 prune を含めない。

## 実装手順

### 1. 計画と責務の統一

- `docs/devcontainer-implementation-plan.md` の CI ビルド・公開、ARM64 runner 導入、
  ロック再生成の責務、更新・復帰要件を本書に合わせる。
- `AGENTS.md` の「CI image-update policy」をビルド場所に依存しないイメージ更新方針に改める。
- CI 容量対策の PR #11 はマージ状態と差分を確認する。未マージなら後継の CI 簡素化を
  反映した時点で取り下げ、マージ済みなら不要な cleanup 呼び出し・専用スクリプト・
  テスト・GC 設定例を後継変更で整理する。共有 runner の設定変更は伴わない。

### 2. CI の静的検証への限定

- `.forgejo/workflows/image.yml` を検証用 workflow に変更し、名称・ジョブ名を責務に合わせる。
  main の push、pull request、手動実行の起動条件は保持する。
- `make test` と `check-common-lock`、`check-dns-lock`、`check-go-lock`、
  `check-rust-lock` を実行する。各呼び出しが Docker を必要としないことを確認する。
- シェル構文検査と ShellCheck、既存の Node.js による
  `tests/test_npm_release_age.cjs` の実行を組み込む。
  workflow の YAML と埋め込んだシェルも検査対象とする。
- `check-locks`、イメージのビルド、コンテナ内検証、公開、公開用環境変数、
  CI イメージ cleanup を workflow から除く。
- runner の必要ツールは Bash、Make、Git、jq、Mike Farah yq v4、ShellCheck、Node.js と npm とする。
  checkout の認証情報を作業ツリーに残さない設定を保持する。

### 3. ローカル更新と検証の入口

- `build` と `rebuild` の既存用途を保持し、利用するイメージだけを更新できる入口を用意する。
- 派生ビルドの Make 依存関係を整理し、検証済み共通イメージの参照をそのまま使用できるようにする。
  未生成のベース参照は明確なエラーとし、別イメージへの暗黙の代替を行わない。
- CI で実施していた検証の組み合わせをローカル向けにまとめる。
  共通は `verify`、`smoke`、`smoke-daemon`、`smoke-remote`、
  DNS は `verify-dns` と `verify-dns-lock`、Go は `verify-go`、
  Rust は `verify-rust` と `verify-rust-lock` を対象とする。
- ビルド参照・結果を記録する入口と、更新前の状態バックアップ・旧参照への復帰手順を用意する。
  自動的な停止・切り替え・状態削除は更新コマンドの副作用に含めない。
- `check-locks` と `update-locks` はローカル操作として保持する。
  更新 PR のマージ前に、対象イメージのビルド・検証と必要なロック再生成の結果を記録する。

### 4. 利用文書の更新

- 実装に合わせて README の通常手順をローカルビルド・検証・選択・起動に変更する。
  `pull` を残す場合は、任意の配布イメージを取得する補助操作として位置付ける。
- `docs/ci.md` は静的 CI の範囲と、ローカル検証の責務を説明する。
  過去の成功実行と現在の運用を区別し、古い公開タグの列挙は必要最小限にする。
- ARM64 CI、公開イメージの pull 障害調査、定期公開・レジストリ保持方針は、
  通常利用の完了条件から外す。インフラ派生イメージとネットワーク実験は別作業とする。

### 5. 移行確認と後片付け

- 変更後の Forgejo CI が Docker へのアクセスなしで成功することを確認する。
- 利用端末で共通イメージと実際に使用する派生イメージをビルド・検証し、
  選択した参照で起動する。認証を伴うスマホ接続の実確認は利用者が行う。
- ローカル運用の成立後、このリポジトリ専用の `REGISTRY_USER`・`REGISTRY_PASSWORD`
  を Actions 設定から削除する。共有トークン自体の失効は他用途の有無を確認する。
- 既存の runner イメージ・キャッシュとレジストリ成果物は、他ジョブ・利用端末からの参照を
  確認した上で管理者が整理する。Docker やレジストリ全体の一括削除を移行手順に含めない。

## 検証と完了条件

- 文書間で CI・利用端末・ロック更新の責務が一致する。
- CI の全ターゲットが Docker なしで成功し、workflow にビルド・公開・全体 prune がない。
- Make のドライランと必要なテストで、派生ビルドが指定した共通参照を使用することを確認する。
- 実装で変更したイメージは Docker が利用可能ならビルドし、ツール・非 root 実行・
  sudo 制限・バージョン記録を確認する。実行できない検証は未確認として記録する。
- 利用端末のマウント、状態保持、リモート停止処理が成功し、更新失敗時も旧参照を利用できる。
- 実際の認証・ペアリング再利用と状態バックアップ・復元は、モックテストとは別に確認する。
- CI 成功だけでは依存の取得、インストール、実行時の互換性を保証しない。
  未実施のアーキテクチャや派生イメージは、利用前のローカル検証を必要とする。

## 変更の分割

1. 設計・AGENTS 方針と静的 CI への変更。
2. ローカルビルド・検証・参照記録の入口と、それに対応する利用文書。
3. 実運用確認後のリポジトリ専用 Secret と不要成果物の管理者による整理。

各段階でコードと説明を整合させる。文書だけで未実装の運用を README の既成事実として扱わない。
